## 2026-09-10 — the object store (port + two adapters)
* **Addition**: `control_plane/object_store.py` — the byte half of the storage boundary. `ObjectStore` (`put(key, source: Path, *,
  content_type)`, `open(key) -> ByteSource | None`) and `ByteSource` (`size`, `content_type`, `read(start, end)`), both `Protocol`. **`put`
  takes a path and `open` returns a stream — neither says `bytes`** (an hour of stereo Opus should not be held in memory).
  `FilesystemObjectStore` is the no-S3 dev default (production code; content type in a `<name>.content-type` sidecar to match S3's round
  trip). `S3ObjectStore` uses `upload_file` + `head_object` + ranged `get_object`/`iter_chunks`. `object_store_from_env()` picks by
  `S3_BUCKET`.
* **Decision — range semantics identical in both adapters** (one `_resolve_range`): inclusive both ends; an `end` past EOF is **clamped**; a
  `start` at/beyond EOF reads **nothing**; a negative bound **raises** (416 is the handler's decision, not the port's). Keys validated the
  same way, `..` included.
* **Decision — no `delete`** (retention is manual; a `delete` would be dead code someone wires up later without reading the decision).
* **Measured, not assumed**: a `head_object` **404 does not prove the object is missing** — a HEAD has no body, so botocore reports a bare 404
  for a missing *bucket* exactly as for a missing key (verified against MinIO); `open` confirms with `head_bucket` before returning `None`.
  boto3's multipart threshold is **8 MiB** (not S3's 5 MiB), so the suite uploads 9 MiB and asserts the ETag part count.
* **Addition**: `tests/test_object_store.py` (39 tests) — one behavioural set over both adapters + three S3-only facts; the S3 half runs
  against a **real MinIO** and **errors rather than skips** without one (18 passed / 21 errors on a machine with no object store).
* **Change**: `test_architecture.py` gains `test_isp_object_store_adapters_satisfy_the_port` (built with `__new__`; `S3ObjectStore.__init__`
  builds a client). `check.sh` uses `tests.infra up all` (adds MinIO); still `missing()`, not `skip()`.
* **Nothing is wired up yet** — `repository.py` still appends chunks straight to `RECORDINGS_DIR` and reads a whole recording into memory; the
  chunk → spool → finalize state machine S3 needs lands with the next work package.

## 2026-09-14 (WP0 of `docs/INTERVIEWER_PRACTICE_WIZARD_PLAN.md` — the update route)
* **Context**: the portal's *New interview* wizard becomes three steps (Basics → Expectations → Preview) shaped like BrewVoice's *New role*, so it saves the interview on **step 1** and draws the expectation toggles on **step 2**. Until now `POST /interviews` was the only write and step 2 had nothing to write to. WP0 is the whole of this repo's share; WP1–WP4 are `skillbrew-organization`.
* **New — `PATCH /api/v1/interviews/{interview_id}`** → `InterviewResponse`, 404 on an unknown id through the same `status:false + message` envelope every other 404 uses. Body `InterviewUpdateRequest {expectations?, report_sections?}`; nothing else on the record is editable, because the job spec, the mode and the language are creation's.
* **Changed — `control_plane/schemas.py`.** The two `InterviewCreateRequest` field-validator *bodies* are lifted to module functions `validate_expectations(v)` / `validate_report_sections(v)`; the create validators now call them and behave identically (its existing tests are the proof). **Both return `None` unchanged when given `None`**, and that guard is the difference between a 422 and a 500: the update model's fields are optional, so an explicit `"expectations": null` reaches the field validator, and pydantic maps only `ValueError`/`AssertionError` to a 422 — a `TypeError` from iterating `None` escapes the envelope unhandled. Sabotaging the guard turns `test_patch_with_an_explicit_null_is_422_not_500` into exactly that `TypeError`, which is why the test is named after the status code.
* **Decision the plan left open: an explicit `null` is *absent*, not *empty*.** A `model_validator(mode="after")` rejects a body where both fields are `None`, so `{}`, `{"expectations": null}` and `{"expectations": null, "report_sections": null}` are all 422 — an update that edits nothing would still move `updated_at`, and a request editing no field is a mistake rather than an identity. A `null` **beside** a real edit is simply skipped: `{"expectations": null, "report_sections": {...}}` applies the sections and leaves the checklist alone.
* **New port — `InterviewEditor`** (`ports.py`), one method `update(interview_id, req) -> InterviewResponse | None`, satisfied structurally by `InterviewRepository` and added to `tests/test_architecture.py::NARROW_PORTS` (a port not on that hardcoded list is not checked by the ISP/DIP tests at all). Deliberately **not** a fourth method on `InterviewStore`: every route that reads a job spec takes that port, and widening it would hand all of them the ability to rewrite one. No composition with `SessionStore` either — the plan's 409-after-the-first-session rule was dropped before it was built, because it is unreachable within the wizard's flow and a 409 body never reaches the portal's inline error, which makes it the inert guard this repo forbids.
* **Changed — `repository.py`.** `update` builds one `UPDATE interviews SET ... WHERE id = ?` from the fields present, with `create`'s JSON encoding because the reader is `get`'s. `updated_at = ?` is always appended — it is what keeps the `SET` clause non-empty whatever else is present, so there is **no branch for a body that edits nothing** and none is needed. `cursor.rowcount == 0` is how a missing row becomes `None`, rather than a second `SELECT`; then `self.get(interview_id)`.
* **The trap, pinned on purpose.** The update validators *are* the create validators, so there is no merge with the stored row: a short `expectations` list gets every omitted fixed item back **enabled** (the restore rule cannot know which omissions were deliberate) and loses every omitted drafted and custom item, and a short `report_sections` map resets the keys it omits to the code defaults. `test_a_partial_patch_list_re_enables_fixed_items_and_drops_drafted_ones` exists so this is documented behaviour rather than a discovery, and it is why the client sends the whole list and all eight section keys.
* **Tests.** 12 added to `tests/test_expectations.py` (42 total): the wizard's real payload stored and read back exactly, a reworded fixed item, a 13th custom item, an unknown section key, the empty body, the explicit `null` (422 not 500), a `null` beside a real edit, an unknown id → 404 with the envelope asserted, each field alone leaving the other untouched, the partial-list pin, and `updated_at` moving — read from the column directly, since `InterviewResponse` does not carry it. Two sabotages re-run before keeping the tests: the `None` guard removed (2 fail with `TypeError`), `updated_at` left unwritten (1 fails).
